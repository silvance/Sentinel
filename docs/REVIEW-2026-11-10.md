## High

### H1. 'setup --force' on a machine with the service installed strips the service account's access to the config folder, then aborts

*Drives, service, security* · `src/sentinel/launcher/setup.py:314`

**What happens:** A technician runs 'Sentinel.exe setup --force' to change a setting after 'winsvc install'. write_setup protects folders in order, config folder first. The config folder's DACL contains the service SID and Users, so prepare_private_dir sees foreign trustees. Its contents (sentinel.toml, camera.secret, *.bak) all count as Sentinel's own, so protect_existing replaces the DACL with setup-account+SYSTEM+Administrators, and sentinel.toml re-inherits it. Next, the spool folder also has the service SID; it holds recordings (CAM01/...), which are not in _OWN_NAMES, so _check_reprotectable raises SetupError. The technician sees 'Setup not completed', but NT SERVICE\SentinelRecorder can no longer read sentinel.toml. Setup then tells the technician to restart the recorder; at that restart, or the next reboot or crash restart, the service cannot open its configuration and recording stops for good (see the next finding for why this is silent). When it succeeds (empty spool/data), the same function also removes the service's Modify right on spool/data/logs and the operators' read on status. write_secret also writes camera.secret without the service SID.

**Evidence:** write_setup: `for folder in dict.fromkeys([config_path.parent, *(... spool_dir, data_dir, log_dir, status_dir)]): prepare_private_dir(folder)` (l.314-317). prepare_private_dir (l.196-198): `elif winacl.foreign_trustees(...) or not ...startswith('D:P'): _check_reprotectable(path); winacl.protect_existing(path, sid)`. _OWN_NAMES (l.175) has no recording or sentinel.db names. Nothing in cmd_setup (launcher/cli.py l.189-214) checks whether the SentinelRecorder service is installed.

### H3. An open 'planned' gap (scheduled_pause / motion_idle) absorbs a later camera outage, and exports label the outage 'planned'

*Recorder core* · `src/sentinel/db.py:884`

**What happens:** Motion schedule: the run ends with MOTION_IDLE, so a gap opens with reason motion_idle. Motion is then detected (or the detector fails and fail-safe recording starts), but the camera is offline, so every retry ends with connect_timeout/ffmpeg_error. Each retry's GapJob calls begin_gap, which only bumps attempts on the open gap and keeps the original reason and detail. _end_run (supervisor.py:572) also skips the run_end event because a gap is already open. When footage resumes hours later, the whole interval is recorded as one gap with reason motion_idle, and the review export (export/manifest.py:37-38) tells the reviewer 'No motion was detected outside the recording hours (motion-triggered recording; planned)'. The same thing happens with scheduled_pause when the camera is dead at the scheduled resume time: the unplanned outage after the resume is reported as 'paused by the recording schedule (planned)'.

**Evidence:** begin_gap: `if row is not None: ... UPDATE recording_gaps SET attempts=attempts+1, ended_run_id=? WHERE gap_id=?` leaves reason, start_basis and detail unchanged. The manifest maps reason 'motion_idle'/'scheduled_pause' to text that says 'planned'. Status code also treats such a gap as a pause (service.py:636 gap_is_pause), so outage length after a restart falls back to uptime. Nothing ends the planned gap at resume and opens a new unplanned one.

### H4. False CRITICAL R-005 'Recording stopped ... recordings are not being saved' after every reconnect, schedule resume or motion wake

### M2. set-camera-credentials / set-camera: during a race window any local user can read the DPAPI machine-scope secret

*Drives, service, security* · `src/sentinel/winsvc/credstore.py:48`

**What happens:** The config folder gets Users:(OI)(CI)RX at install. write_protected_credentials creates '.camera.secret.<pid>.tmp' with tmp.touch(), so it first inherits Users read, and only then runs icacls. A standard local user watching the folder (ReadDirectoryChangesW is allowed with RX) opens the empty temp file for read with FILE_SHARE_READ|WRITE|DELETE before icacls runs. Changing the DACL does not revoke an open handle. The DPAPI blob is then written through Python's shared-write open, and os.replace succeeds because the attacker shared delete. The attacker reads the blob through the still-open handle. Machine-scope DPAPI (CRYPTPROTECT_LOCAL_MACHINE) is decryptable by any process on the machine, and the entropy is public in the source, so the attacker recovers the camera password. docs/07_SECURITY.md states 'ACL restricted before the secret is written'; it is restricted, but only after other users could already have opened the file. winacl.write_private_file (CreateFileW with a protected DACL, share 0) already exists and is what setup.write_secret uses.

**Evidence:** credstore.py l.46-56: `tmp = path.with_name(f'.{path.name}.{os.getpid()}.tmp'); tmp.unlink(missing_ok=True); tmp.touch()` then `cp = run(argv)` (icacls), then `open(tmp, 'r+b')` writes the blob. Used by `winsvc set-camera-credentials` and by launcher/setcamera.write_credentials when the service is installed. commands.install_plan grants `*S-1-5-32-545:(OI)(CI)RX` on the config folder.
