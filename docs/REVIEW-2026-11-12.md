# Overnight review, 2026-11-12 (version 0.3.11)

Nine reviewers (recorder; time, schedule and motion; ledger; archive; drives; export; window; platform and update; deployment walkthrough) read the code. Every medium-or-worse finding went to a skeptic who tried to refute it. The review ran twice: run A stopped at the account's spend limit, resumed later, and finished after run B. Run B: 43 confirmed, 5 refuted, 38 low (not verified). Run A: 47 confirmed, 2 refuted, 46 low. Many findings appear in both runs.

This is a code review, not a forensic validation of the system.

resumed after the spend limit while 0.3.12 was being written and reviewed those uncommitted changes too; that is
how it found rows 10 and 11.

Not fixed from run A's high list in the same way: the stale known-good concern in row 15's finding (rolling back to
an old `.good`) is reduced by row 15 but not removed. Existing `camera.secret.good` files written by earlier versions
keep the folder's ACL until the next passing check rewrites them (row 14).

**Needs a repair on the laptop:** fixes 1, 7 and 8 change the install plan. After installing 0.3.12, an
administrator runs System › Service › Install / repair service once. Up to 0.3.12 that button stopped at "already
installed. Run 'uninstall' first" on a computer where the services exist (finding A, medium); with the follow-up
fix it repairs in place: `sc config` instead of `sc create`, every permission step again, the archive copy paused
during the repair and started again, the recorder left recording. With a 0.3.12 build, use Remove service… and then
Install / repair service… instead (recordings, settings and credentials are kept). Not verified on the laptop:
the new ACL steps were run against real files on the development PC only (not elevated, no installed
service); `icacls /setowner` and the archive service's access to `requests` need the bench run.
