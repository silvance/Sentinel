# Branch `design/windows-service`

## 1. Summary

On Windows the recorder can now be installed as a real Windows service. It starts when the
computer starts, with nobody logged in. It restarts by itself after any failure, with no limit
on the number of restarts, and at Windows shutdown it stops cleanly so the last recording is
finished. A built-in watchdog restarts the recorder if it ever freezes. This works on Windows and
Linux. On Windows the camera password is stored encrypted with Windows' own protection (DPAPI)
instead of as readable text, and the folders holding recordings are restricted to the service
and administrators. The recorder also checks whether the Windows clock is being synchronised.
Installing the service needs administrator rights, which the development machine does not have.
So the installation commands were generated and tested but **not run** on a real Windows
service; the first administrator install on the target PC is still outstanding.

## 2. Requirements addressed

| ID | How | Stated requirement or design choice |
|---|---|---|
| U8 (days unattended, recover without anyone checking) | Auto-start at boot, SCM restart-forever, internal watchdog, graceful pre-shutdown stop, stop deadline | Requirement; all mechanisms are my design choices (below) |
| U9 (fully Windows-compatible; click-to-run, dependencies beside it) | Stdlib-only service host (ctypes), works unchanged in a PyInstaller **one-folder** build; one-file builds explicitly ruled out for the service | Requirement; mechanism my choice |
| U1/U7 (non-technical operators, plain errors) | Watchdog shows R-006 (existing catalogue wording); installer/status messages in plain words; no new operator codes | Requirement |
| E1 (documented clock source, measured offset) | `clock_synchronized()` on Windows via `w32tm /query /status`; T-002 when Windows Time is not running/synchronised | Requirement; partial (sync *state*, not measured offset) |
| E5 (restricted access) | DPAPI credentials, credentials-file DACL check (startup refused if too wide), directory ACLs, virtual service account | Requirement; mechanisms my choice |

## 3. Design decisions and alternatives

### 3.1 Auto-start + restart: a real Windows service, hosted with ctypes

| Option | Before login | Least privilege | Restart forever | Graceful stop at shutdown | PyInstaller one-folder | Verdict |
|---|---|---|---|---|---|---|
| **(a1) pywin32 `win32serviceutil` / `pythonservice.exe`** | yes | yes (any account) | yes (SCM failure actions) | yes (SvcStop / SvcShutdown) | supported by PyInstaller hooks | Rejected: ~10 MB third-party binary dependency with a post-install step (DLL/registry), known venv problems; the project avoids runtime dependencies (docs/01 §5). Gives nothing ctypes cannot. |
| **(a2) ctypes service host (chosen)** | yes | yes | yes | yes — recorder runs *in* the service process, pre-shutdown control calls `request_stop` directly | yes, same process | **Chosen**: no dependency, ~250 lines, protocol logic unit-tested with a fake SCM; the real `StartServiceCtrlDispatcherW` call is exercised (returns "not started by SCM" outside a service). |
| (a3) Wrapper exe (WinSW / NSSM) launching `sentinel.service run` | yes | yes | yes | only via console Ctrl-C emulation | yes | Rejected: an extra third-party executable to vendor and vet (NSSM unmaintained since 2017); a service has no console, so the graceful stop path depends on the wrapper's tricks. |
| (b) Task Scheduler "At system startup" (`schtasks /Create /XML`) | yes | yes | **no**: restart count max 999; Microsoft documents the restart setting for a task that *fails to start* — a program that exits with an error is not reliably restarted (not verified here) | **no**: ending a task terminates the process; no shutdown notification → last segment not finalised | yes | Rejected (also needs `ExecutionTimeLimit` disabled or it is killed after 72 h by default). |
| (c) Startup folder / Run key | **no** (needs a logged-in user) | — | no | no | — | Rejected. |

Configuration (all generated by `python -m sentinel.winsvc install`, see `--dry-run`):
* `sc.exe create SentinelRecorder binPath= "<exe> …host --config …" start= auto obj= "NT SERVICE\SentinelRecorder"`
  — **virtual service account**: no password to manage, its own SID (used in the folder ACLs),
  not an administrator, normal outbound network access (RTSP to a LAN camera needs nothing more).
  Rejected: LocalSystem (far too much privilege), NetworkService/LocalService (shared with many
  other services, so ACLs cannot single out Sentinel), a dedicated local user (password to store
  and rotate; expires by default).
* `sc.exe failure … reset= 86400 actions= restart/5000/restart/30000/restart/60000` — the SCM
  repeats the last action for every subsequent failure ("Subsequent failures" in services.msc),
  so it never gives up. `sc.exe failureflag … 1` makes a STOPPED report with a non-zero exit code
  (config problem, supervisor crash, watchdog) a failure too.
* `sc.exe sidtype … unrestricted`, `sc.exe privs … SeChangeNotifyPrivilege` (drops all other
  privileges from the token).
* Pre-shutdown timeout 180 s via `ChangeServiceConfig2W(SERVICE_CONFIG_PRESHUTDOWN_INFO)`
  (`sc.exe` has no sub-command for it). Plain SHUTDOWN notification gives only a few seconds.
* Source installs only: the service runs the **base** interpreter (a venv's `python.exe` is a
  redirector that starts a child process, which the SCM would not accept) with `PYTHONPATH`
  supplied through the service's `Environment` registry value.
* Exit-code mapping: 0 → clean stop (no restart); otherwise `ERROR_SERVICE_SPECIFIC_ERROR` + code
  → restart. A non-zero exit *after a requested stop* is reported as a clean stop so an
  administrator's stop is never undone. Stop deadline 600 s (finaliser can legitimately take
  up to 60 + 330 s) then exit 6.
* Safety: preflight refuses to install if the service account could not read the interpreter,
  the package, the config or FFmpeg (e.g. a per-user Python install — the case on this dev PC),
  if `[tools]` paths are not absolute (the service does not see a personal PATH), and it refuses
  to re-permission drive roots, system or profile folders or their ancestors.
* `uninstall` stops and deletes the service registration only; recordings, ledger, logs,
  configuration, credentials and ACLs are left untouched.

### 3.2 Watchdog (all platforms)
`sentinel/watchdog.py` + `RecorderService`: the recording loop's `_tick` beats; a thread checks
every `min(5 s, timeout/4)`. After `[service] watchdog_timeout_s` (default 120 s, minimum 5; a
warning below 60 s because a normal run end pauses the loop up to ~50 s) it: logs CRITICAL, dumps
all thread stacks (`faulthandler`) to `logs/watchdog-<UTC>.txt`, writes status R-006 built without
the supervisor's locks or the ledger, records `watchdog_restart` in the ledger, sends FFmpeg `q`
(so the open segment ends cleanly), then `os._exit(5)`. Every step runs in its own thread with a
time limit, so a deadlocked lock cannot prevent the exit. FFmpeg dies with the process (job
object / PDEATHSIG). Disarmed on stop requests (shutdown is supervised by the service manager /
host stop deadline).

### 3.3 DPAPI credentials
`CryptProtectData` with `CRYPTPROTECT_LOCAL_MACHINE | CRYPTPROTECT_UI_FORBIDDEN` and fixed
application entropy, via ctypes. File format: first line `SENTINEL-DPAPI-CREDENTIALS v1 scope=…`,
then base64 — detected by content, so `credentials_file` in the config works for either format
and Linux is unchanged. Machine scope is required because the administrator writes the file and
the virtual account reads it; consequence: the file's ACL is the real barrier (docs/07).

### 3.4 ACLs
`icacls` commands with `*S-1-…` SIDs (language-neutral) are generated; checking uses the
security descriptor as SDDL via `GetNamedSecurityInfoW` + `ConvertSecurityDescriptorToString…`
instead of parsing `icacls` output, because `icacls` prints localised account names. SYSTEM is
kept with full control (Windows components run as SYSTEM and it can take ownership anyway).

### 3.5 Clock sync
`w32tm /query /status`: error HRESULTs matched by number; "service not running" →
**not synchronised** (T-002). Rationale: on stock Windows the time service is trigger-started
and syncs about weekly; an undisciplined PC clock drifts seconds per day, which is not adequate
for multi-day evidence. Labels are English; on a non-English Windows nothing is recognised and the
result is "unknown" (no alert) rather than a guess.

* `w32tm` output of a *running, synchronised* time service: not captured (service stopped here,
  starting it needs admin). Those parser tests use the documented layout and must be re-captured

* DPAPI decryption **by the virtual service account** of a blob written by an administrator

  Windows): not measured.
* Linux: nothing Linux-specific was run (the watchdog is cross-platform and exercised on Windows).

## 7. Risks, limitations, open decisions

1. **First real install on the target PC is the acceptance test** (docs/07 Windows checklist:
   install, reboot with nobody logged in, `taskkill /F` restart, shutdown finalises the last segment).
2. Python/Sentinel/FFmpeg must live where the service account can read them (`C:\Program Files`),
   not in a user profile; the installer refuses otherwise. The PyInstaller packaging branch must
   provide a service entry point (`sentinel.winsvc.__main__:main`) and must be **one-folder**.
3. Owner decision: T-002 is shown whenever Windows Time is not running. On stock Windows that is
   the normal state, so deployment must set Windows Time to automatic with an approved NTP
   source, or operators will see a permanent warning (intended, for E1). A measured clock offset
   (`w32tm /stripchart`) is not implemented.
4. Owner choice (see §9, 2.1): operators read status from a separate status folder; default
   readers = local group "Sentinel Operators" (accounts must be added to it), alternative = all
   local users. The ledger history the GUI sees is at most 5 minutes old (snapshot).
5. The camera password is still visible in FFmpeg's command line to administrators (B4).
6. Watchdog default 120 s: a hang is detected within ~2 min; footage during the hang and restart
   is lost and recorded as a gap by startup recovery.

## 8. Recommendation

**Merge after** (1) the integration suite is re-run on a quiet machine to rule out the
intermittent short-freeze failure as a regression, (2) an administrator runs the docs/07 Windows
deployment checklist on a test PC (install, reboot, kill, shutdown), and (3) the `w32tm` output
of a synchronised machine is captured into `tests/unit/test_w32tm.py`. The pre-existing
hard-kill test failure (`disk I/O error`, also on `main`) needs its own fix. The in-process parts (watchdog, DPAPI, ACL checks, clock parser,
service-host protocol) are tested and safe to merge now; the service registration is the only
part whose real behaviour has not been observed.

### Cross-branch integration (not changed here)
* **`host` sub-command.** My binPath for a frozen build is `"<exe>" host --config "<cfg>"`. The
  single-executable branch's `Sentinel.exe` has no `host` command. Integration options: (a) add a
  `host` sub-command to `Sentinel.exe` that calls `sentinel.winsvc.__main__.cmd_host`, keeping one
  exe; or (b) ship a second, console-less `SentinelService.exe` in the same one-folder build whose
  entry point is `sentinel.winsvc.__main__:main` with `host` as its default. I recommend (b): the
  operator-facing exe stays simple and the service exe can be built without a window, and the
  install command just points `host_command(frozen=True, executable=…SentinelService.exe)` at it.
  Either way the build must stay one-folder (one-file re-launches itself as a child, which the SCM
  rejects).
* **Config / secret layout.** The other branch uses `Sentinel\sentinel.toml` + `camera.secret`; mine
  uses `Sentinel\config\sentinel.toml` + `camera.dpapi` plus separate spool/data/logs/status folders.
  The credentials loader detects DPAPI vs plain TOML by content, so the file *name* does not
  matter: either name works. What does matter for the service: the configuration must be in its
  own folder (installer re-permissions it: Administrators change, service + Users read), separate
  from spool/data/logs/status. Proposal: adopt `C:\ProgramData\Sentinel\config\sentinel.toml` and
  `…\config\camera.secret` (keeping the other branch's file name, DPAPI content on Windows), and
  have that branch's first-run wizard call `set-camera-credentials`' writer
  (`winsvc.credstore.write_protected_credentials`) instead of writing plain text.
